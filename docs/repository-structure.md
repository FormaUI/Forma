# Forma Repository Structure

Forma is a reusable Blazor component library: .NET 11, C# latest, Razor Class Libraries whose components render in a Web App's interactive render modes, Server, WebAssembly and Auto, JS-free by default. This document describes the repository as a codebase: what the solution is made of, where things live, what it derives from, who consumes it, and how it is built and verified; the working rules in `CLAUDE.md` point to it. Where the project stands and what comes next is [the features status](features-status.md), and what each month added is [the feature history](../FEATURE-HISTORY.md). An area with a technical design takes two documents beside this one while it is being built: `{area}-design.md`, the design alone, and `{area}-implementation-plan.md`, the steps and what has landed. The plan is retired once every step has landed and nothing is open, so a finished area carries its design alone.

## Solution structure

Every project is named family plus concept, with the family one of `Framework`, `AddOns`, or nothing for the product: `Forma.Framework.Icons`, `Forma.Framework.JavaScript.Interop`, `Forma.AddOns.Emojis.Twemoji`, `Forma.Blazor`, `Forma.Framework.Composer`. The family says what a project is: Framework is what Forma builds on, whether or not the product itself uses every piece of it; an AddOn is a project that is both optional and built on a Framework assembly it extends. Optional alone makes nothing an AddOn. Every family with more than one project sits in its own folder under `src/` named for the family, `Forma.Framework/` and `Forma.AddOns/`; the product, the Showcase and the components that are their own projects, which name no family, sit at `src/` root, and the locale packs sit together under `src/Forma.Locales/`, which groups them as a family folder does without naming a family, since they are many and alike.

- `Forma.Blazor` is the product, the components. It references the feature assemblies its components need and no more; anything a component works without belongs behind a package a host opts into. Infrastructure that is not a component but serves several, such as the emoji sprite loader, lives under `Features/{Name}/` in the namespace `Forma.Blazor.Features.{Name}`.
- `Forma.Blazor.Server`, `Forma.Blazor.WebAssembly` and `Forma.Blazor.WebView` are the product's render-mode halves: what only a server, only a WebAssembly client or only a Blazor Hybrid application needs beside the components, `FormaPageHead` and the registration of the circuit's integrations on the server's side. Each sits at `src/` root and builds on the product, which references none of them, so the components load in every runtime.
- `Forma.Blazor.{Component}` is a component big enough to be its own project and its own package, such as `Forma.Blazor.Explorer` and `Forma.Blazor.Composer`. Each sits at `src/` root, is laid out as `Forma.Blazor` is and builds on it; the product never references any of them, so the library stands complete without them. One may depend on another when its own markup composes it; a capability that joins two components which otherwise stand apart is an AddOn instead, so that neither depends on the other, as browsing stored files joins the composer to the explorer.
- `Forma.Blazor.Locales.{Language}` is a **locale pack**: an assembly of locale files alone, compiling no code, carrying the files of the assemblies it localizes rather than of itself, such as `Forma.Blazor.Locales.Hebrew`. A pack extends no Framework assembly, so it is no AddOn; it is named for the product family it carries, as a component that is its own project is, and the packs sit together in `src/Forma.Locales/`. Forma's own are one per language and carry every assembly the library localizes, since Forma owns all of them; that naming is this repository's convention rather than something the library enforces, which reads nothing out of a pack's name. An application references a pack and a library never does, since which languages ship is the application's decision. `localization-design.md` is authoritative for what a pack holds and how it is read.
- `Forma.Framework.*` is what other Forma assemblies build on: contracts, defaults, base shells, design vocabulary, horizontal concerns, visual or not. A Framework assembly references only Framework. A Framework assembly is either a default shipped beside its contract and named for the contract plus what it supplies, `Forma.Framework.{Concept}.{Supply}`, such as Unicode emoji or the library's own artwork, or a concept of its own, such as input routing or culture routing; the product need not reference every Framework assembly, and `Forma.Blazor` does not reference `Forma.Framework.Localization.Json`. The contract such a component speaks lives here too, alongside every other Framework assembly.
- `Forma.AddOns.*` is a host opt-in that depends on a Framework assembly and extends it, an artwork pack over the emoji or icon contracts, destinations over the share contracts, converters over the resource contracts: the host references and registers it itself, and every AddOn ships as its own NuGet package rather than inside the product's. An AddOn whose markup composes a component depends on that component's package too. Nothing inside Forma references an AddOn; the Showcase and the tests demonstrate them.
- A contract stays with the feature that owns it however many projects reference it, as `IToastService` stays in `Feedback`.

Namespaces and identities:

- Every assembly has one root namespace unique to it, its project name: `Forma.Blazor` holds `Forma.Blazor.*`, `Forma.Framework.Icons` holds `Forma.Framework.Icons.*`; the test support projects' are `Forma.Tests` and, for the bUnit support, `Forma.Tests.Blazor`; a locale pack compiles no code and so owns no namespace at all. A folder and its namespace stay in step, so `Forma.Blazor/Components/Symbols/` holds `Forma.Blazor.Components.Symbols`; the family folder a project sits under, `Forma.Framework/` or `Forma.AddOns/`, is not part of that folder-namespace correspondence, since it groups projects by family rather than naming one.
- A contracts assembly split from the engine that implements them shares that engine's namespace, so `Forma.Framework.Composer.Extensibility` compiles into `Forma.Framework.Composer`: the split is a packaging boundary rather than a second concept, and a type moving across it must not change a caller's `using`.
- An AddOn owns no namespace of its own and maps to what it extends: `Forma.AddOns.Share.Targets` compiles into `Forma.Framework.Share.Targets`, and `AddOns` appears in code only in the AddOn's static asset base path and in its test project's namespace. A component that is its own project borrows the product's namespace the same way, so `Forma.Blazor.Composer/` holds `Forma.Blazor.Components.Composer` and a host reaches it through the lines it already writes, and the product's render-mode halves borrow `Forma.Blazor` itself, so `FormaPageHead` stays in `Forma.Blazor.Components.Page` and every registrar is reached through `using Forma.Blazor;`.
- Three identities stay in step: the one name an assembly and its namespace carry, `Forma.Blazor`; the package name, that name under the reserved prefix and without the product's own, `formaui-net.Blazor`, which the root targets file derives for every packable project so none declares a `PackageId`; and one static asset base path per assembly that ships assets: `_content/{assembly name}` for a product, a component that is its own project or an AddOn, `_content/forma/{name}` for an interop assembly. `AssemblyName` is never set where it would repeat the project name. The packages publish under the `FormaUI` organization, whose prefix the identifier carries and whose name the package metadata states.

Packaging:

- Every project under `src/` but the Showcase is a package: the product, every component that is its own project, every AddOn, every locale pack and every Framework assembly, a new one included. A Framework package provides a reusable capability, an engine such as the composer's or the explorer's among them; a product package composes those capabilities and supplies the product's integration and defaults. Which types a host may name is decided by their visibility, never by how an assembly ships, so what no caller names stays internal.
- A locale pack is packable and depends on `Forma.Framework.Localization` alone, whose attribute the targets file in its package stamps a referencing project with. It never depends on the assemblies it localizes, since a host installs a pack beside whichever of them it already has, and nothing it holds is reached by name.
- A feature whose contracts something outside it extends keeps those contracts in an assembly named for their role, as `Forma.Framework.Composer.Extensibility` stands beside the engine `Forma.Framework.Composer`, so an extension depends on the contracts alone and never on the engine. Such a package carries no registrar and constructs nothing.
- A model two surfaces browse alike is a feature assembly of its own, named for the model and rooted in its own namespace, as `Forma.Framework.Catalog` is beside the explorer's engine: it takes what a host or a second surface reuses, the items, how they arrive, what the host is asked, and the bookkeeping every surface repeats, and never a surface's settings or what that surface's parts read, which stay in each surface's engine. Two surfaces then share the package without either depending on the other.
- A package depends on packages alone and declares each one its own code requires, never one it reaches only through another. A component that is its own project depends on the product's package, and on another component's where its markup composes it. Every package ships at the one version the root build properties set, so a package depends on the others at the version it was built with.
- A Framework assembly that talks to the browser does so through an interop assembly, a package like any other that ships its scripts under its own static asset base path, so a script keeps its address whichever package brings it to a host.

Registration:

- A feature with services to register has a `ServiceCollectionExtensions` at its project root, registering with `TryAdd`, named for what lands in the container: an artwork package adds a pack named for its source, `AddFormaTwemojiPack()`; a feature whose defaults are services is `AddFormaFeedbackServices()`. The exceptions: culture routing registers through `CultureRoutingExtensions`; the product's server half registers on the host's builder through `HostApplicationBuilderExtensions`, its WebAssembly half through `WebAssemblyServiceCollectionExtensions` and its WebView half through `WebViewServiceCollectionExtensions`, since all three borrow the product's namespace, whose `ServiceCollectionExtensions` a second class of that name would collide with; and a share destination the host switches on one by one, `AddFormaDiscordSharing(configure)`, is added rather than tried.
- `Forma.Blazor` ships one aggregate registrar, `AddFormaUI()`, fanning out to every default a component needs in any render mode. Each render-mode half ships one more that calls it and adds its render mode's halves, `AddFormaUIServer()` on the host's builder, `AddFormaUIWebAssembly()` and `AddFormaUIWebView()`, so a host makes one call on each side; a Framework half that serves a render mode names its registrar for it, `AddFormaCultureServer()`, `AddFormaCultureWebView()` and `AddFormaBrowserServer()`.
- A component whose optional contract is unregistered falls back to a default the library carries, as `FormaIcon` does with the library's own glyph artwork; a contract carrying data nobody can synthesize, such as an emoji catalog, leaves the component in its empty state instead.

## Components

Components live in `src/Forma.Blazor/Components/{Category}/`, where a category names a UI role: `Bars`, `Feedback`, `Inputs`, `Navigation`, `Layout`, `Windows`. A component with supporting types of its own may take a folder inside its category, as `Debugging/InputInspector/` does. A component large enough to grow sub-components and ship as its own package, such as `Explorer` or `Composer`, is instead its own project directly under `src/`, laid out the same way but with no `Components/{Category}/` wrapper, since the project itself is the category. A component is a file set:

```text
Components/{Category}/
├── FormaX.razor          # markup
├── FormaX.razor.cs       # logic
└── FormaX.razor.css      # isolated stylesheet
```

Every component derives from one of three bases in `src/Forma.Blazor/Components/`: `FormaElementBase` for a component a host places, `FormaInputBase<TValue>` for a form input, `FormaComponentBase` for a part that only lives inside its owner. `component-foundations-design.md` is the design.

The library ships three cultures: `en` as the source language, `he` and `es`. A component's strings are a section of its category's file in each language's pack, `src/Forma.Locales/Forma.Blazor.Locales.{Language}/Forma.Blazor/Components/{Category}/{culture}.json`, keyed by the English source text; a component that is its own project has a folder of its own in each pack, named for its assembly. The sibling repository `Forma.Locali` ships `locali`, which checks locale files against the `L[...]` call sites that key them.

Scripts ship with the project that owns them:

- A product built on the component library ships the scripts only it uses itself, under its `wwwroot/scripts/`, with their wrappers in its `Interop/` folder, served as `_content/{Product}/scripts/`: `Forma.Blazor.DataView` its selection, column-fit, height and card-grid behaviors, `Forma.Blazor.Explorer` its layout tier, and `Forma.Blazor.Composer` the rich text editor and the behaviors around its canvas.
- `Forma.Framework.JavaScript.Interop` holds the interop bases, `JSModule`, `JSInterop` and the `IJSEnvironment` they take, and the scripts every other script builds on: the report to a .NET owner, the selectors of the controls a list leaves alone, the frame scheduler, the reading direction, the scroller lookup, the markup sanitizer.
- `Forma.Framework.Browser.Interop` holds the browser capabilities the component library's components use or several products share: the DOM watcher and engine at its root, each capability area in a folder of its own, such as `Scrolling`, and, until their areas replace them, behaviors, operations and component scripts under `wwwroot/scripts/behaviors/`, `operations/` and `components/`, with wrappers in the matching `Behaviors/`, `Operations/` and `Components/` folders. `Forma.Framework.Browser.Blazor.Server` connects it to an Interactive Server circuit.
- A Framework feature with scripts of its own ships them in `Forma.Framework.{Feature}.Interop`, scripts directly under `wwwroot/scripts/` and wrappers at the assembly root, as `Forma.Framework.Input.Interop` serves `scripts/InputRouter.js` beside `InputRouter.cs`.
- DOMQL, the query language the DOM watcher and engine take, lives in the sibling [DOMQL](https://github.com/FormaUI/DOMQL) repository, checked out beside this one as `formaui-net.DOMQL`; it is a JavaScript library published as the package `formaui-net.DOMQL`, whose one bundled file is served as `_content/domql/domql.js`, and a project here that uses it references the package project at `nuget/Forma.DOMQL.csproj` by path, which references nothing here.
- The interop assemblies are served side by side as `_content/forma/core`, `_content/forma/browser`, `_content/forma/input`, `_content/forma/culture` and `_content/forma/culture-router`. A script reaches another assembly's script by climbing to the content root, `../../../core/scripts/FrameScheduler.js` from a behavior and `../../forma/core/scripts/FrameScheduler.js` from a product's script, so the import survives a host path base.
- `FormaComposer` is the one component allowed external JavaScript libraries, each to be confined to its own `Forma.AddOns.Composer.{Capability}` package behind a plugin contract, as `composer-design.md` lays out.

Stylesheets: `src/Forma.Blazor/wwwroot/forma-tokens.css` holds every token, value-only; `forma-reset.css` is cross-browser normalization; `forma-base.css` is the opt-in element-level look; `forma-input.css` is the one input box every field draws; `forma-prose.css` is the look of a document the composer authored. Component rules live in the component's isolated stylesheet.

## The Showcase

`src/Forma.Blazor.Showcase` is the review surface: one interactive page per component under `Components/Pages/{Category}/FormaXPage.razor`, its strings a section of the category's locale pair, rendering every state the component can enter in all three cultures; the data view's, the composer's and the explorer's pages sit under `Features/`. A page opens with:

```razor
@page "/x-component"
@attribute [ShowcasePage("FormaX")]
@rendermode InteractiveServer
@inherits ShowcaseComponentBase
```

`ShowcaseComponentBase` gives the page its strings, `L`, read in the culture state's cultures, and renders it again on each change of the state; a page that shows nothing interactive leaves the render mode out.

and is structured as `<h1>` plus `<p class="description">`, then one `demo-section` with `<h2>` and `demo-box` per scenario. It runs a compiled binary with no hot reload:

```powershell
dotnet run --project src/Forma.Blazor.Showcase
```

A running Showcase holds its `bin` DLLs open, so it is stopped before a rebuild. `src/Forma.Blazor.Showcase/bin/Debug/net11.0/Forma.Blazor.dll` being newer than the sources is the proof a rebuild reached it. `scripts/Start-Showcase.ps1` does both, with `-Force` stopping the one already listening and `-Port` choosing where; it sets the address and the environment itself rather than leaving them to the launch profile, which is not checked in and so exists only where a project has been run from an editor.

## Tests

Every production assembly should have one test project named after it under `tests/`, as does the one thing tested there that is not an assembly, the glyph drawing rules in `tests/Forma.Scripts.Tests`, mirroring the source paths, so component tests live under `tests/Forma.Blazor.Tests/Components/{Category}/`, and a component that is its own project takes a test project named after it, as `FormaXTests.razor` with a `FormaXTests.razor.cs`. The exceptions, each covered from elsewhere: `Forma.Framework.Share`, a contracts assembly whose behavior shows only through what extends it, is exercised through `tests/Forma.AddOns.Share.Targets.Tests`; `Forma.Framework.Composer.Extensibility`, for the same reason, through `tests/Forma.Framework.Composer.Tests`, which tests the engine implementing it; `Forma.Framework.Media` and `Forma.Framework.Toolbar` through the components that use them in `tests/Forma.Blazor.Tests`; the locale packs, which compile no code, through the component tests, whose bUnit context reads the packs as an application does; and the scripts of `Forma.Framework.Browser.Interop` and the products through the script test project, with the wrappers of its kind folders driven from the tests of the components and features that own them.

- `FormaBunitContext` in `Forma.Tests.Support.Blazor` is the shared test context of every component test project; it registers localization, the Twemoji pack and `AddFormaUI`. That project holds what a component test needs and a Framework test must not pull in, bUnit and the product itself, so `Forma.Tests.Support` stays free of both and every test project can reference it.
- `tests/Forma.Tests.Support` holds every fake, fixture and utility, in a folder mirroring the production area it serves, such as `Resources/`, `Media/` and `Interop/`, with `Shared/` for what no area owns and the namespace following the folder: `Forma.Tests.Resources`, `Forma.Tests.Shared`, `Forma.Tests.Interop`. `FakeJSRuntime` and `FakeJSObjectReference` drive interop wrappers; `FakeLoggerFactory` reads what was logged; `StubStringLocaleFactory` reads what strings were asked for.
- `tests/Forma.Blazor.Tests.Scripts` runs the `wwwroot/scripts/` modules of every assembly that ships scripts under Vitest and happy-dom, reaching each through an alias named for the assembly's concept, `#core/`, `#browser/`, `#input/` and `#culture/` for the interop assemblies and `#composer/`, `#dataview/`, `#explorer/` and `#showcase/` for the products and the Showcase, with that assembly's tests in a folder of the same name laid out as its `wwwroot/scripts/` is.
- The browser check drives the components in a real browser, headless, in each runtime a Web App renders them in. `tests/Forma.Blazor.Browser.Host` is a Web App with a Server, a WebAssembly and an Auto page, and `tests/Forma.Blazor.Browser.Host.Client` is its client, the minimal one a host builds: the components and their WebAssembly half alone. `tests/Forma.Blazor.Browser.Full` is a standalone client referencing every package a client can load, published to measure what each optional package adds and served as a standalone app, its files as a static host serves them. `tests/Forma.Blazor.Browser.Tests` is the check itself: an xUnit program run by the gate's browser step after it publishes both clients in Release, never by `dotnet test`. It holds each client's compressed download, by dependency group, to the budgets in its `budgets.json`, which a reviewed change raises when a package grows on purpose, and records which assemblies the publish trims. Its culture checks run against the host started in several modes: islands and an interactive router switching through culture addresses; islands switching the culture state alone, rendering every request in a named culture and, apart, in the invariant culture, so no check rests on the culture of the machine it runs on; islands persisting a switch in the culture cookie, which request localization reads back; islands beside a client culture each WebAssembly runtime keeps as its own, with culture capture off, the host handing the runtime its arrangement through an environment variable at `Blazor.start`; and a recording router in each runtime for the navigation checks; and against the full client served as a standalone app. `tests/Forma.Blazor.Browser.Components.Checks` holds the component checks' pages, a Razor class library the components host and its client render and the WebView check host renders too: a check page per component, its address naming the runtime, `server`, `webassembly`, `auto` or `webview`, which the host's `App` renders the interactive router in, or `static`, which it renders statically, with the services the checked components need; `tests/Forma.Blazor.Browser.Components` and its client host them in a Web App, and a test class per category in the check's `Components/` folder drives each component's interactions, every call it makes to a script and every call a script makes back among them, in the Server, in WebAssembly, in Auto twice, on a first visit, which runs on the Server, and once WebAssembly has downloaded, which runs there, and in the web view, each case asserting the runtime it ran in, and the static check renders every check page statically, holding it to show its state, raise no error, show nothing waiting on a script and offer no enabled control whose action needs interactivity, while an inventory holds every component the catalog lists to a check page and every check page to a check that runs in every interactive runtime; the host is apart from the minimal client, whose download stays what a host using no component pays. `tests/Forma.Blazor.Browser.WebView` is the WebView check host, a WPF application whose native windows each render the components to a web view, registered through the product's WebView half before or after the platform's registrar, as an environment variable says, with culture routes and strings of its own embedded in it, which also renders every component's check page, each component check opening a native window of its own at its page and closing it as it ends, one at a time; the browser step publishes it on Windows, the one platform WebView2 runs on, and each of its checks starts an application of its own and drives its web views through WebView2's DevTools, alone once every other check has run, since a whole application would compete with the timing of the checks beside it, and reports itself skipped elsewhere. `tests/Forma.Examples` holds the example hosts, a Web App and its client for each culture arrangement and an application for each Blazor Hybrid host, WPF, Windows Forms and MAUI on Windows, set up as the library's README sets a host up and behind build files of their own, so they reference Forma's packages and take nothing from the repository's build; the browser step packs the solution at `1.0.0-examples`, a version only they use, clears it from the machine's package cache, publishes them and drives them, and holds each README block tagged with an example's file to that file. What the code does today is a plain check, and a requirement it doesn't meet yet is a known failure, carrying the `Kind` trait `KnownFailure`, which passes while the requirement fails and fails once it is met, so the change that meets it makes it a plain check.

## Build and verification

`build.ps1` at the root runs the gate, so a person and a machine run the same checks; `-Target` narrows it to `DotNet`, `Scripts` or `Browser`, and `-Clean` deletes build output, alone or before a run. A task program is built outside the repository, in the SDK’s own place in the system temp directory, and every edit and rename leaves the folder before it behind there, so `clean.ps1 -All` sweeps those too; it checks that a folder holds nothing but what the SDK put there rather than trusting its name, and it reaches past this repository to anything else run from a single file on the machine. It covers every command below but the last, builds the task programs written in C#, which no other step reaches, and checks each task script's shape. Beside the module under `scripts/build/` sit the narrower loops, one lowercase script each: `compile.ps1`, `test.ps1`, `format.ps1`, `tasks.ps1`, `browser.ps1`, `mobile.ps1` and `clean.ps1`, where `browser.ps1 -Visible` runs the browser check in a browser window a person can watch, and `mobile.ps1 -Platform` builds the MAUI example host from the packed packages for `Android`, `iOS` or `MacCatalyst`, which no other step reaches, since each needs its platform's MAUI workload and Apple's need a Mac; CI's mobile job runs it on Linux for Android and on a Mac for the other two. They exist so a run that only needs one project’s tests does not wait for the whole gate: `test.ps1` takes `-Target`, `-Project`, `-Filter`, `-NoBuild`, `-Times`, `-LoadWith` and `-WaitLog`, where a repeated run continues past a failure so that a test failing sometimes shows as a rate, `-LoadWith` runs other test projects over and over beside it to load the machine, and `-WaitLog` names the folder the waits a component test makes with diagnostics record themselves in, cleared of an earlier run's records first and read back as the waits that needed time. Each of them is a wrapper: what an action does lives in `scripts/build/Forma.Build.psm1`, so the gate and a single action cannot disagree about what a build is. The test step shows each test project as it finishes, with how many have finished and the time left against the run before, and closes with the totals and the failing tests by name; every step’s heading gives the time it took the last time it passed, kept under `artifacts/build/`. Every action understands `-WhatIf`, which is what lets `scripts/build/build.tests.ps1` assert what each script does by running it without doing it, because a step that quietly ran nothing would otherwise look exactly like a step that passed. A description is not everything, though: a step whose body is wrong describes itself perfectly, so cleaning and the wait log are also run for real there against folders made for the purpose. The gate reads every script in `scripts/` for the shape one here keeps and exercises those it can run without a side effect, through `scripts/Test-TaskScript.ps1`; a script added and covered by nothing fails there, so it is covered or it belongs under `.local/` as nobody’s to maintain. The locale lint restores `locali`, pinned in `.config/dotnet-tools.json`, and runs it over the solution, so a machine without it fetches the pinned version rather than skipping the step. A component project imports `eng/ComponentAnalyzers.targets`, which bans the members that read or set the ambient culture through `eng/BannedSymbols.Components.txt`, so a component that reaches for `CultureInfo.CurrentCulture` fails the build with the culture state member to use instead. Every library a WebAssembly client loads builds with Forma's own analyzers in `eng/Forma.Analyzers`, tested by `tests/Forma.Analyzers.Tests` and shipped in no package, whose rules keep each type that crosses the interop boundary serializable once trimmed, and whose generator keeps every annotated type's members with its library, since the trimmer applies an annotation only where code asks a value typed as that type for its type. On Windows the browser step also publishes the Blazor Hybrid example hosts and drives them through WebView2, closing a native window as its close button does; the MAUI one builds against the `maui-windows` workload, which a Windows machine installs once, from an elevated shell, with `dotnet workload install maui-windows`, and which CI's Windows run installs itself, and the step stops at once, naming the command, where it is missing. The showcase never exits, so it stays a check made by hand, started through `scripts/Start-Showcase.ps1`.

A release is made through `publish.ps1` at the root, which takes the version to release and the feed to publish to, the organization's GitHub feed, nuget.org or both. Every package ships at the one version the root properties file holds, so the script writes that version there and commits it, packs the solution in Release, marks the commit with a signed annotated tag named for the version alone, `1.0.0-preview.1`, pushes the commit and the tag together, and pushes each package. It refuses a version any chosen feed already holds for any package, a tag of that name on another commit, a branch behind its upstream, and uncommitted changes, so a package always matches a pushed commit and a published version is never overwritten; `-WhatIf` lists what a release would do after passing the same checks. A tag therefore marks exactly the commits packages were built from, and there is one per released version and none otherwise.

```powershell
dotnet build Forma.slnx
dotnet test Forma.slnx
dotnet format Forma.slnx --verify-no-changes
dotnet tool restore
dotnet locali --path Forma.slnx --severity warning
npm test --prefix tests/Forma.Blazor.Tests.Scripts
./scripts/build/browser.ps1
dotnet run --project src/Forma.Blazor.Showcase
```

`TreatWarningsAsErrors` is on for `src` and `tests` alike; the `.editorconfig` severity table decides what the compiler reports, and the root file and the per-project files beneath it, such as `src/Forma.Blazor/.editorconfig`, differ deliberately. No project sets `GenerateDocumentationFile`; a throwaway build lists the undocumented public members:

```powershell
dotnet build Forma.slnx -p:GenerateDocumentationFile=true --no-incremental -v:q -nologo |
    Select-String CS1591
```

Work that belongs to a person rather than to the repository lives under `.local/`, ignored in its entirety: the benchmarks, the spikes, and a document written for a piece of work rather than for the repository itself. One ignored root takes the place of a rule per directory, so something new that is nobody else's business needs no rule at all, and nothing kept there can be staged by accident.

The build is entered through `build.ps1` at the root, with its module and its wrapper scripts under `scripts/build/`. A build script is named for its action in lowercase, `compile.ps1` and `test.ps1`, because it is a command someone types rather than a cmdlet they discover; the functions inside the module are PowerShell functions and take `Verb-Noun` with an approved verb, as PowerShell requires of anything a module exports. Everything else in `scripts/` is a task script: PowerShell 7, cross-platform, named `Verb-Noun.ps1`, such as `Get-TwemojiPack.ps1`, `Build-GlyphPack.ps1` and `Update-PluralRules.ps1`, beside `BrandMarks.psm1`, the module the brand-artwork scripts share. `Stop-MsBuild.ps1` and `Stop-DotNet.ps1` are there for the build that fails to copy a file nothing appears to be using: MSBuild keeps its workers alive between builds and they hold what they last built, and the second goes further and stops whatever is running out of the repository too. Both ask for the supported shutdown before stopping anything, and neither reaches the language server an editor runs for C# unless it is asked to. What decides which a thing is, is whether the build runs it: a script the gate would run belongs to the build, and one that fetches artwork, generates a checked-in asset or drives a browser against a running Showcase does not. Work a script cannot do in PowerShell without writing C# through it, browser automation and glyph geometry so far, is a file-based C# program under `scripts/cs/` that the script runs: `Test-ComponentScale.ps1` runs `cs/CheckComponentScale.cs`. A check built around a tool of its own keeps everything for that tool in a folder named for it, its program included, beside the script that runs it: `Test-ScreenReaderSpeech.ps1` runs `nvda/CheckScreenReaderSpeech.cs` with the speech recorder NVDA loads from the same folder. A program there is named for what it does in PascalCase without the hyphen a cmdlet name carries, since it is a file rather than a command, and the script that runs it keeps the approved verb. A program declares the packages it needs in its own header, which is why central package management stops at `scripts/` rather than reaching into it. A program that is an entry point opens with a shebang, and the gate builds each one, since nothing else compiles them. A file included into a program rather than run takes a plain noun for a name, as `GlyphParser.cs` does, and logic in a program that is worth testing moves into such a file, which the program includes and `tests/Forma.Scripts.Tests` compiles.

## Origins

Every component derives from the legacy admin application, which sits outside the workspace in a repository of its own:

| What | Where |
|------|-------|
| Admin design system | `App_Themes/Cms/css-3.6.5.css`, `fa-3.6.5.css`, `global-3.6.5.css`, `responsive-3.6.5.css` |
| Page markup | `admin/*.aspx` and `admin/pops/*.aspx` |
| Behavior and rendering helpers | Matching `*.aspx.cs` files |
| Replaced jQuery widgets | `admin/Client/{toggle,date,cp,modal,Tabs,jcrop,minibar}` |

The legacy admin's boxy gradient toggle becoming a token-driven iOS-style `FormaToggleSwitch` is the intended level of fidelity: the real states, vocabulary, edge cases and required behavior survive; the visuals are Forma's.

## Consumers

The current consumers are the admin application Forma first served and **Épica Deportiva**, brought in by project reference or local NuGet. Épica's own documentation lists the subset it requires and tracks its status.
