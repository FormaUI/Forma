# Forma Localization Layout Implementation Plan

The plan for reading locale files into the entries [the localization design](localization-design.md) states: what the runtime, the build and the linter do today, the steps the change lands through, their gates, their state, and where the build departs from the design.

## What stands today

**The runtime reads by layout at every lookup.** `LocaleSource.Read` walks a type's name from the root down to the type, matching the assembly's paths against its files at each level, and applies what it finds level by level, a file closer to the type winning. A source is one of three kinds, each with its own layout: an assembly's embedded files, read by `LocalePath.Defaults`; a host's folder, a folder per assembly read by `LocalePath.HostDefaults`; and a pack, read as a host's folder is.

**The build sorts files by their place.** A file in a folder directly inside the project's root `.locales` is a host's, for the assembly the folder names: an application embeds it under the reserved prefix `.locales.`, and a library leaves it out. Every other file is the project's own and takes the SDK's resource name, which turns a folder named `es-419` into `es_419`. A pack names its files itself, by their paths.

**The linter reads a file's culture from its name alone.** `LocalizationFileName.GetCulture` reads the last part of a file's name, so a file in a culture folder, such as `.locales/es/Accounts.Admin.json`, carries no culture for it and is passed over by the rules that place files: the project's own files, a host's and a pack's.

**What was proven before the plan.** A source given the resource names the build forms read `.locales/es/Accounts.Admin.json`, `.locales/es/Accounts.Admin.UsersPage.json` and the root's `.locales/es.json` with one path added to its defaults, `$RootDir/$LocalesDir/$Culture/$AnchorName$Extension`, beside the existing folder layout. The type's own file won over the namespace's file for the one key both gave. MSBuild's `AssignCulture` tells a culture folder (`es`, `es-419`, `he`, `zh-Hant`) from an assembly's folder (`Forma.Blazor`) without failing on either.

## Steps

Each step ends buildable, tested and reviewable, and passes the fast gate.

1. **A baseline of lookup costs.** ✅ A benchmark of the first lookup in a culture and of later lookups, over Forma's own Spanish and Hebrew packs and an application's own files, recorded before step 2 changes the runtime. Gate: the numbers recorded beside this plan's state. Measured with BenchmarkDotNet 0.14 on .NET 11, in process, `es` and `he` within a few percent of each other, the mean of the two given:

   | Lookup | Forma.Blazor's types from the packs | An application's 200 types in 50 namespace folders |
   |---|---|---|
   | The first, with a new factory | 495 µs, 321 KB | 735 µs, 636 KB |
   | The first of every type, with one new factory | 857 µs, 800 KB | 2.16 ms, 2.6 MB |
   | A later one, already read | 114 ns, 56 B | 95 ns, 56 B |

   The first lookup in a culture already reads every file a source places in it, since a source finds the `@.` sections by reading them all, so reading an assembly's files for a culture once adds no reading the runtime does not do today.
2. **Reading into entries.** ✅ A source reads an assembly's files for a culture once into entries, applying the default reading of the design's *Reading a file* or the assembly's stated paths, and expanding `$shared` and `@.` sections as it reads. A lookup chooses by the design's *Precedence*, culture first and source second, and settles a conflict within a source by the file whose name sorts last, logging each conflict once as a warning naming both files. Sources become one kind, read by one rule: an assembly's own files, a pack, the application, and the folder beside it. `SearchedLocation` and every message name files from what an entry remembers. Gate: a unit test for each case the design names, every existing localization test passing or changed for a decision the design records, and the culture and localization browser checks passing in every runtime. Departures: a pack and a host's folder read the default reading with the assembly's name leading every name rather than standing where their names begin, so a culture folder can stand before it; the default templates are gone, which Locali's own pack source overrides, so Locali builds against this branch again only at step 6, and steps 2 to 6 reach `dev` together; and the README and the changelog describe the default reading at step 5, when the build lets a project's root `.locales` hold a culture folder.
3. **The cost, measured again.** ✅ The benchmark of step 1 over step 2's runtime. Gate: the numbers recorded beside step 1's, and any lookup slower than the baseline explained, or made lazy per assembly and culture where the first lookup in a culture costs more than it did. Measured as step 1 was, against its numbers:

   | Lookup | Forma.Blazor's types from the packs | An application's 200 types in 50 namespace folders |
   |---|---|---|
   | The first, with a new factory | 449 µs, 315 KB: 9% faster, 2% less | 764 µs, 695 KB: 4% slower, 9% more |
   | The first of every type, with one new factory | 746 µs, 653 KB: 13% faster, 18% less | 1.94 ms, 2.23 MB: 10% faster, 14% less |
   | A later one, already read | 114 ns, 56 B: the same | 100 ns, 56 B: the same, within the runs' spread |

   The first reading measured slower, 549 µs and 886 µs, until three changes in the step: a source keeps, for each name, the sections that give it and copies a type's entries only when the type is read; a name is parsed once for a source, and only where it holds the culture asked for; and a file read in full under a name starting with the root namespace is left out of the full-name reading, which no type it could answer consults. An application's first lookup still costs a little more than it did, the price of indexing every section of the culture's files where the walk read only the type's own; every lookup after it costs less.
4. **Faster lookups.** ✅ Every path a string passes through, from reading a file to rendering its text, made faster and lighter wherever a change keeps each result and each error the same. A culture-bound locale keeps what it read for each of its cultures; a factory answers a type it has made a locale for from the type alone; a key's holes and a text's plural expressions are read once for as long as the text lives; a rendering writes its text, and each value through its hole's format, into a stack buffer; a count's plural form is chosen without allocating; a file is read in one pass of a JSON reader; and a type's entries are gathered without splitting its name or asking its assembly for its name again. Gate: every localization test passing, and the old and new code giving the same result, or the same error, on every locale file in the repository and a hundred crafted ones, most of them malformed, and on every pairing tried of a value, a hole's format and alignment, and a culture. Measured as step 3 was, against its numbers:

   | Lookup | Forma.Blazor's types from the packs | An application's 200 types in 50 namespace folders |
   |---|---|---|
   | The first, with a new factory | 389 µs, 239 KB: 13% faster, 24% less | 638 µs, 533 KB: 16% faster, 23% less |
   | The first of every type, with one new factory | 603 µs, 458 KB: 19% faster, 30% less | 1.57 ms, 1.77 MB: 19% faster, 21% less |
   | A later one, already read | 35 ns, nothing allocated: 70% faster | 38 ns, nothing allocated: 62% faster |

   An application's first lookup, a little slower than step 1's after step 2, is now 13% faster than it. Two lookups the benchmark gained in this step, over the packs, against step 3's runtime: a later one rendering a count, `{Count} selected`, takes 374 ns and 112 B against 662 ns and 916 B, and a factory making a component's locale again takes 6.5 ns and allocates nothing against 957 ns and 1.4 KB. Five candidates were left as they were: a satellite probe, over a quarter of a first lookup, stays once per factory, since WebAssembly loads a culture's satellites when the culture is chosen and a miss remembered longer could hide one loaded since; a bound locale stays one per component, since sharing one per type and culture would key a cache by culture instances, which a host can create without end, to save a small object and a cached read for each; a file's metadata and a section's name each cost under one percent of a first lookup; and the build reads each JSON file whole, since a file's marker may stand anywhere in it.
5. **The build.** ✅ Every locale file is embedded under the project's root namespace and its path with `/` made `.`, named by the build itself; the reserved prefix `.locales.` goes; `LocaleReferenceAttribute` names each referenced application that embedded locale files; and a pack's culture check reads a culture folder as well as a file's name, deciding a culture as the runtime does. The `Forma.Framework.Localization` README's *Where locale files live* says, in order, the model every file is read into, the layouts that read the same and the rule behind them, another assembly's strings in an application and a pack, which text wins by culture, then source, then within a source, and another layout by paths; every other README that describes where locale files live or the reserved prefix follows. Gate: the build's own cases, and an application whose `.locales/es-419/` files load in every runtime. Departures: an application's files are read by a source of their own beneath the application's root, which an application is always read through, so the build records any client embedding a locale file and a library embeds its files for another assembly too, read only from an application; a pack's culture check carries the runtime's reading in a task written inside the targets, since MSBuild can't call the runtime, and MSBuild on .NET Framework knows the predefined cultures alone; the browser checks' host routes English and Hebrew alone and registers no backend, so the culture checks read culture folders through the standalone WebAssembly application and the web view, whose files moved into culture folders, passing in every runtime, and the build's own case proves a regional folder keeps its name; and the locale lint warns that the web view's line in `.locali.json` reaches no locale file until step 6's release reads culture folders.
6. **Locali.** Open. The linter places files through the runtime's reading and checks entries: a file's culture from a culture folder or its name; a conflict within one source as an error; an assembly named for a culture, a name fitting two readings, a library file naming another assembly, and a part of a name that is a culture in another case and names no type, as warnings; and its rules about layout (LOC0024, LOC0117, LOC0118) restated over the new reading. Its README and rules document follow, and a release. Forma's part ✅: the default reading of a file's name is public, a source lists every section a type reads whether its entries win or not, and a conflict says whether it is between shared entries. Gate: Locali's fast and full gates, Forma linting clean with the release, and Forma's tool manifest pinned to it.
7. **Forma's own files.** Open. The conflict rule run over Forma's files, and each conflict it reports resolved, such as a file of the Showcase's own folder for its assembly, `.locales/Forma.Blazor.Showcase/`, localizing a key its other files localize. Gate: the locale lint clean.
8. **The documents.** Open. The `Forma.Framework.Localization` README's *Where locale files live*, its *Locale packs* and its settings, and the changelog: a breaking change, since a source's files no longer win by being closer to a type, and an application's files for another assembly lose the reserved prefix. Gate: the documents describe what the runtime, the build and the linter do.
