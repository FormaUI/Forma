# Forma.Framework.Localization

The localization contract, its value types, and the plural machinery a backend evaluates a
translated format with. Everything here is backend-agnostic: a backend registers
`IStringLocaleFactory` and evaluates through this project.

`Forma.Framework.Localization.Json` is the backend Forma ships.

## The contract

| Type | What it is |
| --- | --- |
| `IStringLocale` | Translated strings for one resource base name. |
| `IStringLocale<T>` | The same, for the base name derived from `T`. Adds no members. |
| `IStringLocaleFactory` | Creates locales for a type or for a base name under a location. |
| `LocalizationOptions` | The settings every backend shares, whatever it reads translations from. |
| `LocalizationNotFoundException` | Thrown when a key has no translation and the host requires one. |
| `LocalizedText` | A translated string with the key it was looked up under. Converts implicitly to `string`. |
| `LocalizedArgument` | A value with the name a hole refers to it by. |
| `LocalizedFormat` | Pairs values with a format's holes, and renders a format once they are paired. |
| `LocalizedPattern` | A translated format whose plural forms are resolved and whose holes are still open. |
| `LocalizedSegment` | One run of a format: literal text, or a hole naming an argument. |
| `LocalizedSegmentEnumerator` | Walks a format as segments, slicing rather than copying. |

## Language

| Type | What it is |
| --- | --- |
| `IPluralRuleSet` | Decides which plural category a count falls into for a locale. |
| `PluralCategory` | The six CLDR categories: `Zero`, `One`, `Two`, `Few`, `Many`, `Other`. |
| `PluralOperands` | The CLDR operands a plural rule reads: `n`, `i`, `v`, `w`, `f`, `t`, `e`. |
| `PluralExpressionEvaluator` | Evaluates the plural expression inside a translated format. |
| `CommonPluralRuleSet` | The CLDR rules for every locale it publishes, and the default `IPluralRuleSet`. |

`CommonPluralRuleSet` is generated by `scripts/Update-PluralRules.ps1` and verified against the sample
counts CLDR ships beside each rule. `CommonPluralRuleSet.Default` is a shared stateless instance, and a
host wanting different rules can implement `IPluralRuleSet` itself. Run the script with a
`-CldrVersion` to move to a newer release.

Rules are keyed by locale rather than language, because CLDR carries a few entries that differ by
region or script. The fullest identifier wins and then falls back a subtag at a time, so `pt-PT`
finds Portugal's rules, `es-CO` falls back to Spanish, and `0` is singular in Brazil but plural in
Portugal. `Select` returns `null` for a locale it carries no rules for.

## Files

| Type | What it is |
| --- | --- |
| `LocaleSource` | Where translation files are read from: the walk from the file named for the assembly down to the file named for the type, over a store a derived class opens files from. |
| `EmbeddedLocaleSource` | The files embedded in one assembly, or in a culture's satellite assembly. |
| `HostLocaleSource` | The folder a host keeps its own translation files in. |
| `ILocaleFileFormat` | A format files are written in: its extension, and how one file is read into a `LocaleFile`. |
| `LocaleFile` | One file as read: its sections and entries, and the root it completes a type's name from when it declares one. |
| `LocaleSection` | One node of a file: the sections beneath it and the entries it holds. |
| `LocaleFileEntry` | One translation a file declares, with the name of the type it belongs to. |
| `LocaleSourceEntry` | One translation a source read for a type, with the file and the section it came from. |
| `LocalizationSchema` | The shape of the metadata entry every file carries. |
| `LocalizationMetadata` | Reads and checks that entry; `LocalizationFileMetadata` is what it declares beyond the required fields. |
| `LocalizationMetadataException` | Thrown when a file's metadata does not let it be read. |

## Looking a string up

```csharp
L["Save"]                    // "שמור"
L["Save"].ResourceNotFound   // false when a translation was found
L.GetAllStrings(includeParentCultures: true)
```

The key is the English source text, so a key with no translation renders as written.

## Filling holes

A hole is `{name}`, optionally `{name,alignment}` and `{name:specifier}`. Values pair with the key's
holes by position:

```csharp
L["Stored {stored} of {total}.", written, allowed]
```

| Rule | |
| --- | --- |
| A lookup takes one value per distinct hole | any other count throws |
| A repeated hole is still one hole | `"{n} of {n}"` takes one value |
| A key with no holes takes at most one value | which the name-less plural form reads |
| A hole with no argument renders as written | `{total}` appears literally |

A specifier stays in the key and the value is passed unrendered, so the translation decides the
formatting: `"Ratio {ratio:P1}"` carries its specifier in the key, and a translation may write
`{ratio}` or `{ratio:P2}` instead.

A literal brace is doubled, in keys and in translation files alike: `"Use {{curly}}"` renders as
`Use {`, and its translation writes `{{` too. Doubling is only needed when
the braces would otherwise read as a hole naming an argument that was supplied, because a hole whose
argument is missing already renders as written.

## Plural syntax

```text
[$ [name] plural; category: text; …; $]
```

`[name]` is the argument holding the count, and `#` is that count formatted for the culture. Fields are
`category: text` pairs separated by `; `, and the trailing `;` is required. Categories are CLDR's —
`zero`, `one`, `two`, `few`, `many`, `other` — and a language needs only the ones it distinguishes, so
English uses `one` and `other`, Hebrew adds `two`, Arabic uses all six.

```json
"{files} files": "[$ [files] plural; one: # file; other: # files; $]"
```

Leave the name out when the count is the only value:

```json
"[$ plural; one: # file; other: # files; $]": "[$ plural; one: קובץ אחד; two: שני קבצים; other: # קבצים; $]"
```

That form takes exactly one unnamed value; anything else throws. Expressions use brackets and holes
use braces, so the two never collide. The category comes from
`IPluralRuleSet`, falling back to `other` when the translation omits the chosen field or the language
has no rules. `#` keeps the digits the count was written with, so `0.5` does not round and `1000000` is
grouped for the culture. A malformed expression is left as written.

`#` means the count only inside the field a plural expression selects. Ordinary prose keeps it, so
`"Issue #42 in C#"` is untouched, and so is a `#` inside an expression named for another keyword.
Inside a field a literal `#` is doubled, `##`, which is the only place the doubling means anything —
elsewhere `#` needs no escape and `##` stays as written.

## Settings

`SourceLanguage` names the language the keys are written in, and defaults to `en`. An untranslated key
resolves its plural forms under that language rather than the one on screen.

`RequireMatchingLocalization` turns a missing translation from a fallback into a
`LocalizationNotFoundException`, and defaults to false. Turn it on in development and CI to find what
is untranslated. `GetAllStrings` never throws under it.

`ResourcesPath` names the folder an assembly embeds its translation files under, empty when they sit
beside the types they translate. `LocalesPath` names the folder the host keeps its own translation
files in, `locales` beside the application by default, resolved against the application's base
directory when relative; empty reads none.

## How a file is found

A locale resolves a **base name** from the type's full name, which every `LocalizedText` reports as
the location it searched:

| Type's full name | Base name |
| --- | --- |
| Starts with the assembly name | `{assembly}.[{ResourcesPath}.]{remainder}` |
| Contains a dot but a different root | `{full name}` |
| No dot at all | `{assembly}.[{ResourcesPath}.]{name}` |

Generic arity and nested-type markers are dropped: `Grid<T>` reads `Grid.he.json`, `Outer+Inner` reads
`Outer.Inner.he.json`, and a closed generic resolves through its open definition.

A type's translations sit in the file named for the type, or in a file named for a namespace above
it, where objects complete the rest of the name. Walking down from the assembly, each of these, shown with the JSON backend's extension,
translates `FormaToolbar` in `Forma.Blazor.Components.Bars`:

```text
Forma.Blazor.es.json                    { "Components.Bars.FormaToolbar": { "Bold": "Negrita" } }
Components/Bars.es.json                 { "FormaToolbar": { "Bold": "Negrita" } }
Components/Bars/Bars.es.json            { "FormaToolbar": { "Bold": "Negrita" } }
Components/Bars/FormaToolbar.es.json    { "Bold": "Negrita" }
```

A file named for a folder sits beside that folder or inside it under the folder's own name, and the
two are one and the same; the assembly's file sits at the project root under the assembly's name. An
object's key may spell several segments at once or one at a time, so
`"Components": { "Bars.FormaToolbar": { … } }` reads the same as the first line. A file holds only
the keys it changes: a file closer to the type wins over one higher up, and the type's own file over
every other.

Lookup walks `CultureInfo.CurrentUICulture` outward through `Parent`, taking the first culture whose
files have the key and stopping before the invariant culture, which no file can name. Within a
culture, a file is read from the main assembly first, then from that culture's satellite assembly.
Files are read once and cached frozen.

`ResourcesPath` inserts a folder segment between the assembly name and the remainder. It resolves from
the assembly root, and a type rooted outside the assembly bypasses it.

## Translations from the host

A host lays its own files in a `locales` folder beside the application, to reword a string an
assembly ships, or to add a language it never had. `LocalesPath` names the folder, resolved
against the application's base directory when relative; an empty value reads none.

The folder is laid out as an assembly's own files are, under a folder named for the assembly, so
each of these, shown with the JSON backend's extension, translates `FormaComposer` in
`Forma.Blazor.Components.Composer`:

```text
locales/Forma.Blazor.es.json                                     { "Components.Composer.FormaComposer": { "Bold": "Negrita" } }
locales/Forma.Blazor/Components.es.json                          { "Composer.FormaComposer": { "Bold": "Negrita" } }
locales/Forma.Blazor/Components/Composer/FormaComposer.es.json   { "Bold": "Negrita" }
```

The same precedence applies, and a host's entry wins over the assembly's own at the same position,
so a host file holds only the keys it changes and every other key keeps the assembly's translation.

Host overrides respect culture specificity. Lookup takes a key from the most specific culture that
has it, from either source, before falling back to the parent, so an override written in `es` is a
fallback for an `es-419` reader rather than a replacement for every Spanish string; an override of a
key belongs in the culture that supplies that key.

A host file completes a type's name from the assembly's name, without `ResourcesPath`, so the
host's layout follows the namespace rather than the embedding. An assembly whose root namespace is
not its name has its host files declare the root in their metadata, as
`RootNamespace: Forma.Framework.Resources.Office;`, and the path and sections then complete the
name from there: a file declaring that root at
`locales/Forma.AddOns.Resources.Office/OfficeResourceProvider.es.json` translates
`Forma.Framework.Resources.Office.OfficeResourceProvider`. A file declaring no root, for a type whose
namespace does not start with the assembly's name, is laid out by the type's full name. Files under a
declared root are read after the assembly's own, so their entries win. An embedded file needs no
root, since its name already spells one. Every file carries the [metadata](#file-metadata) entry,
declaring the culture its name gives it.

The folder has to reach the application's output: a web project copies JSON content there on its
own, and any other project marks the folder as content copied to the output directory.

## Reading the layout from a tool

The layout is one rule, and it is public so a tool checks files by the rule the runtime reads them
with rather than by a copy of it. `LocaleSource` owns the walk from the file named for the assembly
down to the file named for the type, over any store a derived class opens a file from by its name
segments, and answers with each entry it read together with the file and section it came from;
`EmbeddedLocaleSource` and `HostLocaleSource` are the runtime's two. A format is an
`ILocaleFileFormat`, which names the extension its files carry and reads one file into a
`LocaleFile`, a tree of sections and entries the contract walks; a backend such as
`Forma.Framework.Localization.Json` is one such format. `LocaleFile` lists every entry a file
declares with the part of a type's name the entry's sections complete, which is the same rule read
from the file's side.

## Patterns and segments

`Resolve` returns the translated format with plural forms selected and the holes still open, so a
caller can render literal text and holes differently — filling a hole with rendered content rather than
text, for instance:

```csharp
var pattern = L.Resolve("Capped at {limit} here.", limit);

foreach (var segment in pattern.Segments())
{
    // segment.IsHole ? the argument whose Name matches segment.Name : segment.Text
}
```

Segments run over the translated format, so a translation may order the holes however reads best.
`LocalizedSegment.Text` is a `ReadOnlySpan<char>` sliced from the format and the enumerator is a
`ref struct`, so walking allocates nothing. A doubled brace arrives as its own single-character run:
`"Use {{curly}}"` yields `Use `, `{`, `curly`, `}`.
